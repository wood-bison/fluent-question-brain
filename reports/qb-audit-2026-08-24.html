Как устроен проект

Канон контента — Go API над одним PostgreSQL (content-схема): question (стабильная identity) → immutable question_revision c SHA-256 content_hash → локали en/ru в question_locale. Поиск стадийный: exact → FTS/trigram → семантика (pgvector, bge-m3 через Ollama) → RRF-фьюжн с объяснимым provenance. Все кросс-системные записи идут через audit_event + outbox.

Зачем CMS — вердикт

Паттерн «CMS как редакторская поверхность над каноническим стором» — правильный и совпадает с консенсусом 2025–2026. Payload даёт бесплатно drafts/versions/diff/локализацию — руками на React Admin/Refine это недели работы.

Модель данных и структура вопросов

Базовая форма — свободный текст: на каждую локаль prompt / short_answer / explanation + произвольные sections в JSONB. Дискриминатора question_type нет нигде. Вместо него три опциональных типизированных блока в payload:

БлокНазначениеПоля
choicesMCQ-скринингoptions[], answer_key, rationale
taskПрактическое упражнениеcondition, starter, solution, walkthrough, difficulty, constraints
rubricОценочная рубрикаlevels[{label, text}]

«Задачи с assert'ами» (Notion JS) — текстовые console.assert(...) внутри секции Task, не исполняемая структура. Исполняемые задачи живут вне Question Brain — во внешнем fluent-task-runtime/tasks/<id>/task.json с обратной ссылкой questionKeys.

ПРОВЕРЕНО question_edge и вся таксономия v1 — schema-only задел без единого Go-writer'а. Пустые таблицы — ожидаемое состояние.

Расширяемость

Форма вопроса синхронизирована в трёх местах: Go-структура canonicalCard (источник хеша), whitelist промоушена, SQL-проекции. Любая новая индексируемая сущность = правка всех трёх.

Дёшево
Новое поле данных в payload — JSONB, хеши старых ревизий стабильны, миграция не нужна
Средне
Новый фильтруемый dimension (как level/company) — ALTER+backfill+индекс + правки ~6 слоёв: canonicalCard, promote whitelist, Search-SQL, search/types.go, CMS collection, browse facets
Средне
Исполняемые задачи — расширить TaskBlock+парсер или развивать внешний runtime-реестр (уже задокументирован в taxonomy.md)
Дорого
Новый тип связи — CHECK-констрейнт в 0001:122 → миграция + инвариант в AGENTS.md

Совпадает с консенсусом ПРОВЕРЕНО

  • Postgres вместо отдельных vector/graph DB — уходить при ~100M+ векторов / измеренном узком месте ГИПОТЕЗА для Question Brain — пока не нужно

Как сделан этот отчёт и почему

Отчёт следует конвенции Trace Dossier из пайплайна pi-html-report. Вот принципы и почему они работают:

1. Вердикт первым

Читатель принимает решение за 10 секунд. Всё после — подкрепление. В外围ing начало с контекста — классическая ошибка технических отчётов.

2. Семантические токены

Каждый цвет — функция: --accent = активный маршрут/важное, --sage = проверенное, --rust = проблема, --gold = внешний/неподтверждённый. Не «красный = плохо» — а «красный = нужна проверка».

3. Семантические стейты

ПРОВЕРЕНО = найдено в коде/primary source. СИНТЕЗ = вывод из фактов. ГИПОТЕЗА = плосибо, но не проверено. СЛЕДУЮЩАЯ ПРОВЕРКА = минимальный эксперимент. Это не маркировка — это контракт достоверности.

4. Terminal-bg для кода

Фон --terminal-bg не меняется между темами. Это значит: .tok-kw, .tok-str, .tok-num, .tok-com — всегда одни и те же цвета. Читатель не переучивается при переключении.

5. Нет градиентов, нет CDN, нет дашбордов

Каждый лишний HTTP-запрос, каждый «красивый» градиент — мусор для print, мусор для screen readers, мусор для модели, которая читает HTML. Сам файл — артефакт; он должен работать автономно.

6. 65–75 символов на строку

Доказано с 2000-х (Baym et al.,订阅阅读研究ы). Длинные строки утомляют; слишком короткие — дробят мысль. .prose { max-width: 68ch } — баланс.

7. Печать как отдельный тест

Если отчёт не читаем в печати — он нечитаем на projector, на экране совещания, в PDF-экспорте. @media print переключает на light, убирает nav/toggle.
