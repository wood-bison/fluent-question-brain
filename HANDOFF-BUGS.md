## BUG-1 · Проверка `ru_prompt_equals_answer` не ловит то, ради чего создана

**Важность: высокая.** Это причина, по которой 70 сломанных карточек прошли
приёмку наряда №2.

**Что не так.** Проверка сравнивает русский вопрос с русским ответом. Но
типичная поломка выглядела иначе: в поле вопроса лежал заголовок раздела из
PDF — `C`, `:`, `-`, `SQL`, `Указатели`, `Jquery`, `DeepCopy`. Такой «вопрос»
ответу тоже не равен, поэтому проверка показывала `0`, а 70 карточек были
непригодны.

**Что сделать.** Заменить проверку на равенство проверкой на осмысленность.
Предлагаемые признаки вырожденного промпта, любой из них:

- короче ~20 символов **и** без вопросительного знака;
- совпадает с полем `title` карточки;
- совпадает с названием темы или её частью;
- состоит из одного слова без знаков препинания;
- равен ответу (текущая проверка — сохранить как один из признаков).

Осторожно с ложными срабатываниями: `Что такое SLA?`, `Что такое Сага?`,
`Что такое каналы в Go?` — **настоящие** короткие вопросы, они не должны
попадать в отчёт. Вопросительный знак здесь и есть отличие.

Ту же проверку применить и к английской стороне: у `av-124` и `av-146`
английский промпт был сломан ровно так же и никакой проверкой не ловился.

**Приёмка:**
```sh
curl -sS /v1/quality | jq '.checks.degenerate_prompts'    # 0
```
Плюс: временно подставить в тестовой карточке промпт `SQL` и убедиться, что
проверка его ловит, а `Что такое SLA?` — нет.

## BUG-7 · Порог релевантности стоит на слитом скоре — конструкция хрупкая

**Важность: средняя.** Работает сегодня, но по построению ненадёжна.

**Что не так.** Отсечка сделана как `rank_score >= 0.02` **после** слияния RRF.
RRF выводится из **рангов**, а не из силы совпадения: первый документ в
полностью мусорной выдаче получает такой же скор, как точное попадание. Порог
`0.02` работает лишь потому, что кодирует правило «два плеча согласились» —
одно плечо даёт 1/61 ≈ 0.0164 и не проходит, два дают ≈ 0.0328 и проходят.
Значит запрос, где полнотекстовый и триграммный поиск оба слабо зацепились за
мусор, отсечку пройдёт.

**Что сделать.** Перенести порог **внутрь каждого плеча, до ранжирования**.
Приятная деталь: у триграммного плеча порог уже встроен в PostgreSQL —
оператор `%` уважает `pg_trgm.similarity_threshold` со значением по умолчанию
`0.3`. Именно триграммы были источником шума в исходном баге, и это
единственное плечо, где ничего изобретать не надо. Абсолютный порог на
семантическом плече уже сделан правильно — косинус это настоящая шкала.

**Важное следствие:** при слиянии через `FULL OUTER JOIN` с `COALESCE(..., 0)`
документ, выживший **хотя бы в одном** плече, всё равно попадает в выдачу.
Пустота на промахе достигается, только когда у каждого плеча свой порог и
**все** вернули ноль строк.

**Приёмка.** Прежние проверки не должны сломаться:
```
"fibonacci generator" en   → релевантная карточка или 0, но не мусор
"event loop" / "idempotency" / "rate limiter" → ≥ 1
"консистентное хеширование" ru → ≥ 1
бессмыслица → 0
```

## BUG-8 · Индексы HNSW и IVFFlat не оправданы и режут полноту под фильтрами

**Важность: средняя.**

**Факты:** в базе лежат `question_embedding_hnsw_dev` и
`question_embedding_ivfflat_dev` поверх **7626 векторов**.

**Почему это плохо.** 1024 измерения по 4 байта ≈ 4 КБ на вектор, то есть
весь набор — около 30 МБ и целиком помещается в буферы. Документация pgvector
прямо говорит, что по умолчанию идёт точный поиск с идеальной полнотой, а
приближённый индекс меняет результаты запросов. Добивающий довод — фильтры:
при приближённом индексе фильтрация применяется **после** сканирования индекса,
а у нас фильтры по теме, локали, уровню и компании. То есть индекс молча режет
полноту ровно там, где выборку сужают.

**Что сделать.** Удалить оба индекса. Порог для возврата к вопросу — сотни
тысяч векторов либо измеренная p95, вышедшая за бюджет; сейчас ни того, ни
другого.

**Приёмка:** индексов нет; поисковые проверки из BUG-7 дают те же результаты
или лучше; замерить и записать в отчёт p95 поиска до и после.

**Приёмка:** `git remote -v` не пуст, `git push` прошёл, история на месте.
